        1. Purpose and Scope
        TEXT
        This document defines the parent requirements for the GHOST Model Context Protocol capability.

        MCP is a first-class GHOST interface family. It is not part of the graphical/human-interface requirement family.

        This document owns the common MCP contract shared by all GHOST MCP capabilities:
        - protocol and transport;
        - client interoperability;
        - authentication and authorization;
        - authenticated owner identity;
        - tool discovery and invocation;
        - request isolation;
        - rate limiting;
        - common error and security behavior;
        - deployment ownership boundaries; and
        - capability-extension governance.

        Detailed functional behavior is owned by the MCP child requirement files:

        - 111_mcp_capabilities.sdoc:
        Prompt Engineering, Episodic Memory, Clipboard Memory, and Collection Memory.

        - 112_mcp_activeblackboard.sdoc:
        all current and future ActiveBlackboard behavior, including the current Persistent Chat prototype.

        - 113_mcp_runtime_control.sdoc:
        MCP-visible GHOST runtime lifecycle control, including remote start, stop, status, readiness, and selectable EC2 runtime profile.

        Runtime, container, local-hosting, AWS, reverse-proxy, HTTPS, Cognito, and deployment realization remain owned by the Runtime Platform and Operations requirement family.

        GHOST-MCP-ROOT
        GHOST MCP Capability Scope
        GHOST shall provide a Model Context Protocol interface through which approved external AI clients can invoke explicitly exposed GHOST capabilities.

        The MCP capability shall provide a controlled external boundary around approved GHOST functions without transferring ownership of those functions to the MCP transport layer.

        MCP shall be represented as its own capability family in the GHOST requirement hierarchy.

        GHOST-MCP-CHILD-DOCUMENTS
        MCP Child Requirement Documents
        The MCP capability shall be decomposed into:

        1. 111_mcp_capabilities.sdoc for all approved MCP capabilities except ActiveBlackboard.
        2. 112_mcp_activeblackboard.sdoc for all current and future ActiveBlackboard behavior.
        3. 113_mcp_runtime_control.sdoc for MCP-visible GHOST runtime life

        The child files shall inherit from GHOST-MCP-ROOT and shall not duplicate the common protocol, authorization, transport, deployment-boundary, or client-interoperability requirements owned by this document.

        GHOST-MCP-INTERFACE-OWNERSHIP
        MCP Interface Ownership
        The MCP parent capability shall own:

        - external MCP protocol behavior;
        - MCP transport requirements;
        - MCP capability negotiation;
        - tool discovery and invocation rules;
        - authenticated caller identity;
        - authorization enforcement;
        - common tool-call rate limiting;
        - interface-visible errors;
        - cross-client interoperability;
        - shared MCP security boundaries; and
        - the boundary between MCP functionality and runtime/deployment realization.

        The MCP parent capability shall not duplicate the internal algorithms of Prompt Engineering, Memory Management, ActiveBlackboard, or other GHOST functional subsystems.

        MCP Tool Provider Role
        The GHOST MCP server shall act as a tool provider.

        An external AI client shall explicitly invoke an exposed GHOST MCP operation.

        The MCP server shall not claim to passively receive, monitor, intercept, or persist ordinary client conversation traffic for which no applicable GHOST tool invocation occurs.

        7. Controlled Extension and Requirement Stability
        TEXT
        The former 73_mcp_interface.sdoc described an earlier, prompt-engineering-only MCP scope.

        Requirements from that document whose engineering meaning remains valid retain their established GHOST-MCP requirement UIDs in this new MCP family.

        Obsolete single-tool exclusions are not reused for a different meaning.

        New MCP functionality receives new UIDs rather than silently redefining unrelated existing requirements.
        REQUIREMENT

        A new MCP capability shall be added only through explicitly approved requirements defining the behavior necessary for that capability.

        The presence of experimental implementation code shall not by itself promote that experiment to a permanent product requirement.

        GHOST-MCP-CONTRACT-CHANGE-CONTROL
        MCP Contract Change Control
        A material change to an approved MCP tool identifier, required input, output semantics, persistence effects, destructive behavior, authorization boundary, or retrieval behavior shall be treated as an MCP interface-contract change.

        The change shall be reflected in approved requirements and corresponding verification before it is treated as the new stable contract.
