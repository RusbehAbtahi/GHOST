        1. Purpose and Scope
        TEXT
        This document owns all GHOST MCP requirements concerning ActiveBlackboard.

        It deliberately contains two different maturity levels:

        1. Current implemented Persistent Chat prototype behavior.
        2. Future ActiveBlackboard vision.

        The Persistent Chat implementation is the first executable stage toward ActiveBlackboard and shall be documented as implementation fact.

        The final multi-chat and multi-actor ActiveBlackboard architecture is not yet fully designed. Future requirements therefore remain high-level and shall not invent unresolved coordination semantics.

        No ActiveBlackboard behavior belongs in 111_mcp_capabilities.sdoc.

        GHOST-MCP-BLACKBOARD-ROOT
        ActiveBlackboard Scope
        GHOST shall maintain a dedicated MCP requirement area for ActiveBlackboard.

        The requirement area shall distinguish:

        - current Persistent Chat behavior that already exists; and
        - future shared ActiveBlackboard behavior that remains under design.

        2. Current Persistent Chat Prototype
        TEXT
        The current implementation provides Persistent Chat Memory as a single-stream prototype of ActiveBlackboard.

        It uses the common GHOST memory infrastructure while applying a dedicated MCP persistence policy.

        The implementation is currently centered on three tools:

        - ghost_persistent_chat_init
        - ghost_persistent_chat_append
        - ghost_persistent_chat_resume

        These names describe current executable behavior and shall not be replaced in the requirements by hypothetical future tool names.

        GHOST-MCP-BLACKBOARD-CURRENT-PROTOTYPE
        Persistent Chat as ActiveBlackboard Prototype
        The current Persistent Chat implementation shall be treated as the first executable ActiveBlackboard prototype.

        It validates:

        - explicit activation of persistent conversation recording;
        - one persistent history across multiple conversation turns;
        - append-only visible Q/A recording;
        - cumulative ActiveBrief continuity;
        - deterministic resume; and
        - owner-scoped persistent state.

        It shall not be represented as the final multi-actor ActiveBlackboard architecture.
        REQUIREMENT

        GHOST-MCP-BLACKBOARD-CURRENT-SINGLE-STREAM
        Current Single-Stream Boundary
        The current Persistent Chat implementation shall be treated as a single continuing chat stream.

        Its use of ActiveBlackboard-related storage naming shall not by itself establish implemented multi-chat, multi-actor, shared-board, or agent-coordination behavior.

        The first episode shall be created only by a subsequent successful append.

        Draft
        Parents:
        • GHOST-MCP-PCHAT-APPEND-TOOL Persistent Chat Append Tool

        GHOST-MCP-PCHAT-VISIBLE-QA
        Persist Complete Visible Q/A
        Each appended episode shall contain:

        - the complete visible user message; and
        - the substantive visible assistant answer produced for that user message.

        The persistence path shall not intentionally replace the visible exchange with a summary.
        REQUIREMENT
        		4.3
        GHOST-MCP-PCHAT-NO-HIDDEN-CONTENT
        Draft
        Parents:
        • GHOST-MCP-PCHAT-VISIBLE-QA Persist Complete Visible Q/A
        GHOST-MCP-PCHAT-NO-HIDDEN-CONTENT
        Hidden Processing Is Not Conversation Content
        Persistent Chat shall not save as conversation content:

        - hidden chain-of-thought;
        - internal model reasoning;
        - MCP protocol traffic;
        - internal tool results;
        - hidden tool arguments;
        - internal application diagnostics; or
        - the GHOST persistence receipt itself.

        Only the visible conversation content selected by the approved append behavior shall form the saved Q/A episode.
        REQUIREMENT
        		4.4
        GHOST-MCP-PCHAT-PRESENTATION-AUTHORITY
        Draft
        Parents:
        • GHOST-MCP-PCHAT-VISIBLE-QA Persist Complete Visible Q/A
        Children:
        • GHOST-MCP-PCHAT-ANSWER-BEFORE-APPEND Answer Then Persist
        GHOST-MCP-PCHAT-PRESENTATION-AUTHORITY
        Client Remains Answer Presentation Authority
        The invoking AI client shall compose the normal complete answer for the user before that answer is persisted.

        GHOST Persistent Chat shall store the supplied answer and shall not become a replacement answer renderer.

        Normal Markdown, code blocks, tables, and other visible answer formatting may remain part of the persisted assistant response.
        REQUIREMENT
        		4.5
        GHOST-MCP-PCHAT-ANSWER-BEFORE-APPEND
        Draft
        Parents:
        • GHOST-MCP-PCHAT-PRESENTATION-AUTHORITY Client Remains Answer Presentation Authority
        GHOST-MCP-PCHAT-ANSWER-BEFORE-APPEND
        Answer Then Persist
        The intended visible interaction order shall be:

        1. compose the normal assistant answer;
        2. append the same substantive visible Q/A to Persistent Chat;
        3. receive the GHOST save result; and
        4. present the normal answer followed by the short persistence receipt when appropriate.

        The persistence receipt shall not become part of the saved assistant answer.
        REQUIREMENT
        		4.6
        GHOST-MCP-PCHAT-APPEND-EXISTING-ONLY
        Draft
        Parents:
        • GHOST-MCP-PCHAT-APPEND-TOOL Persistent Chat Append Tool
        GHOST-MCP-PCHAT-APPEND-EXISTING-ONLY
        Append Does Not Create Missing Persistent Memory
        ghost_persistent_chat_append shall operate only on an existing owner-scoped Persistent Chat memory.

        Append failure shall not silently initialize a new persistent memory.

        GHOST-MCP-PCHAT-BRIEF-UPDATE
        ActiveBrief Update
        For each later episode, the invoking AI client shall construct the updated cumulative ActiveBrief from:

        - the previous latest ActiveBrief; and
        - the current visible user/assistant exchange.

        The resulting ActiveBrief shall represent the updated cumulative state after the new episode.

        Client-Composed ActiveBrief
        The current Persistent Chat prototype shall rely on the invoking AI client to compose the updated ActiveBrief.

        GHOST persistence code shall store the supplied ActiveBrief and shall not require a separate GHOST LLM call merely to recreate the same cumulative summary.

        GHOST-MCP-PCHAT-COMMON-PERSISTENCE
        Common GHOST Persistence Infrastructure
        The current Persistent Chat implementation shall use the established GHOST durable memory infrastructure:

        - MemoryRecord;
        - .ragmem;
        - .ragmeta.json;
        - shared SQLite indexing; and
        - stable file_id / record_id identities.

        Persistent Chat shall not require a parallel unrelated persistence format.
        REQUIREMENT
        		6.5

        Draft

        • GHOST-MCP-PCHAT-COMMON-PERSISTENCE Common GHOST Persistence Infrastructure
        GHOST-MCP-PCHAT-COHERENCE
        Body Metadata and Index Coherence
        Before continuing or resuming an existing Persistent Chat memory, the current implementation shall validate coherence among the durable memory body, metadata file, and SQLite index sufficiently to avoid continuing from an inconsistent identity or episode set.
        REQUIREMENT
        		6.6
        GHOST-MCP-PCHAT-PARTIAL-SAVE
        Draft
        Parents:
        • GHOST-MCP-PCHAT-COMMON-PERSISTENCE Common GHOST Persistence Infrastructure
        GHOST-MCP-PCHAT-PARTIAL-SAVE
        Partial Save Shall Not Be Reported as Success
        If durable episode body data has been written but a later metadata or SQLite update fails, GHOST shall not claim that the episode was coherently saved.

        The failure result may identify the durable Record ID so recovery or repair remains possible.

        A Record ID used for resume shall resolve only within the authenticated owner's Persistent Chat memories.

        A Record ID belonging to another owner shall not expose or resume that owner's persistent memory.

        Resume From Latest Coherent State
        The supplied Record ID shall identify the Persistent Chat history.

        After that history is identified, continuation shall use the latest coherent episode and latest cumulative ActiveBrief belonging to that history, even when newer episodes exist after the supplied resume handle.
        REQUIREMENT
        		7.5

        Draft
        Parents:

        GHOST-MCP-PCHAT-RESUME-STATE
        Resume State
        A successful resume shall provide sufficient state for continued persistence, including:

        - stable persistent file_id;
        - title;
        - description where present;
        - latest Record ID;
        - latest sequence number;
        - latest episode time; and
        - latest cumulative ActiveBrief.

        The exact current response schema may additionally expose related metadata already present in the implementation.

        An individual ActiveBlackboard/Persistent Chat episode may be deleted through the shared deterministic memory Delete capability using an exact Record ID or other approved exact selector.

        Semantic or descriptive deletion shall not be used.
        REQUIREMENT
        		8.3
        GHOST-MCP-BLACKBOARD-DELETE-BRIEF-TRACE
        Draft

        GHOST-MCP-BLACKBOARD-DELETE-BRIEF-TRACE
        ActiveBrief Residual Trace After Episode Delete
        Deleting an individual historical ActiveBlackboard episode does not require rewriting all later cumulative ActiveBriefs.

        A later ActiveBrief may therefore preserve a summarized trace of information that originated in the deleted episode.

        This residual cumulative-summary effect is accepted for individual episode deletion.

        9. Current Prototype Boundary

        GHOST-MCP-BLACKBOARD-NO-CURRENT-MULTIACTOR
        No Current Multi-Actor Blackboard Claim
        The current Persistent Chat prototype shall not be represented as implementing:

        - several cooperating actor streams;
        - autonomous Blackboard agents;
        - Programmer/Auditor/Architect/Requirements coordination;
        - shared multi-chat routing;
        - background Blackboard orchestration; or
        - a completed shared-board GUI.

        Those capabilities belong to the future ActiveBlackboard vision.
        REQUIREMENT
        		9.2
        GHOST-MCP-BLACKBOARD-NO-INVENTED-CURRENT-TOOLS
        Draft
        Parents:

        GHOST-MCP-BLACKBOARD-NO-INVENTED-CURRENT-TOOLS
        No Invented Current Lifecycle Tools
        Current implementation documentation shall identify the executable Persistent Chat tools as Init, Append, and Resume.

        Verify, Close, actor-routing, board-synchronization, or other hypothetical lifecycle tools shall not be claimed as implemented unless corresponding code and requirements are later approved.

        ActiveBlackboard Detailed Architecture Is Open
        The following future ActiveBlackboard decisions are intentionally unresolved:

        - exact actor coordination protocol;
        - exact actor-routing algorithm;
        - shared versus per-actor versus per-stream ActiveBrief ownership;
        - final Blackboard lifecycle operations;
        - automatic versus user-triggered synchronization;
        - exact shared-state selection semantics;
        - exact conflict-handling behavior;
        - final future MCP tool schemas; and
        - final future GUI interaction model.

        These details shall not be invented in requirements until explicitly designed and approved.
