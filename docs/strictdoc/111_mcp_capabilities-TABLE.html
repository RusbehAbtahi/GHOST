        1. Purpose and Scope
        TEXT
        This document defines the approved GHOST MCP functional capabilities other than ActiveBlackboard.

        It owns:

        1. Prompt Engineering.
        2. Episodic Memory.
        3. Clipboard Memory.
        4. Collection Memory.
        5. Shared memory Save, Recall, List, and Delete semantics applicable to these modes.

        All current implementation and future requirements concerning ActiveBlackboard or Persistent Chat belong exclusively to 112_mcp_activeblackboard.sdoc.

        The memory requirements in this document extend GHOST through MCP without requiring a broad rewrite of the established 50-series Memory Management baseline.

        Where the existing core Memory Management infrastructure is reused, its existing requirements remain valid for their original scope.

        GHOST-MCP-CAP-ROOT
        MCP Capability Scope
        GHOST MCP shall support the approved Prompt Engineering capability and three non-ActiveBlackboard memory modes:

        - Episodic Memory;
        - Clipboard Memory; and
        - Collection Memory.

        ActiveBlackboard shall remain separately owned by 112_mcp_activeblackboard.sdoc.

        TEXT
        Prompt Engineering is an already implemented GHOST MCP capability.

        Temporary experimental client-routing forms, including current Prompt:, MEM:, or plain-request mode experiments, are not stabilized as requirements by this document.

        The durable requirement is the GHOST prompt-engineering capability itself.

        GHOST-MCP-APPROVED-FLOW
        Prompt Engineering Processing Flow
        The stable Prompt Engineering processing path shall:

        1. accept the current prompt text;
        2. create isolated request state;
        3. execute existing deterministic PreProcessing;
        4. execute existing A2 PromptShaper on the resulting SuperPrompt;
        5. rebuild the authoritative prompt-ready representation; and
        6. return the engineered prompt.

        Prompt Engineering shall not independently duplicate PreProcessing or A2 algorithms inside the MCP adapter.

        Fresh Prompt State Per Prompt-Engineering Call
        Each Prompt Engineering call shall operate on request-isolated SuperPrompt state.

        Mutable prompt state from another user, request, or earlier tool call shall not be reused as the active processing state for the new call.

        GHOST-MCP-MEMORY-MODEL
        Four-Mode MCP Memory Model
        The approved GHOST MCP memory model shall consist of four conceptual memory modes:

        1. Episodic Memory.
        2. Clipboard Memory.
        3. Collection Memory.
        4. ActiveBlackboard Memory.

        This document owns the first three modes.

        ActiveBlackboard is owned exclusively by 112_mcp_activeblackboard.sdoc.

        GHOST-MCP-MEMORY-COMMON-TRUTH
        Common Durable Memory Infrastructure
        MCP memory modes may reuse the established GHOST durable-memory infrastructure, including:

        - MemoryRecord;
        - .ragmem durable episode bodies;
        - .ragmeta.json metadata;
        - SQLite indexing; and
        - vector storage where required by the owning memory mode.

        MCP-specific semantics shall not require creation of a second unrelated memory truth model when the common GHOST infrastructure can represent the approved behavior.

        Owner-Scoped Memory
        Every persistent MCP memory operation shall be scoped to the authenticated owner.

        An exact key, record ID, Collection ID, Collection Name, Clipboard slot, or other selector shall never bypass owner isolation.

        Save Visible Conversation Content
        When saving a visible conversation episode, the selected visible user content and corresponding visible assistant content shall be stored without substitution by hidden reasoning, internal tool traffic, or an internal model/tool result.

        When exact visible content is required by the selected Save operation, ChatGPT shall pass that content without summarizing it.

        GHOST-MCP-MEMORY-SAVE-TITLE-DESCRIPTION
        Episode Title and Description
        A newly saved ordinary memory episode shall have:

        - an Episode Title; and
        - an Episode Description.

        ChatGPT shall generate both from the selected visible episode unless a more specific mode requirement states otherwise.

        Episode Title is primarily human-facing metadata.

        Episode Description is the compact semantic description used by intelligent Episodic retrieval.

        		4.1.4
        GHOST-MCP-MEMORY-SAVE-RECALL-KEY
        Draft
        Parents:
        • GHOST-MCP-MEMORY-SAVE Shared Save Concept
        GHOST-MCP-MEMORY-SAVE-RECALL-KEY
        Recall Key Handling and Episodic Uniqueness
        When the user explicitly provides a Recall Key, ChatGPT shall pass that key.

        When the user requests an Episodic save without providing a Recall Key, ChatGPT shall generate an appropriate Recall Key rather than forcing the user to invent one.

        Within an authenticated owner's Episodic Memory, the effective Recall Key shall be unique.

        Before saving a new Episodic episode, GHOST shall check the owner-scoped Episodic Recall Keys recorded in the SQLite/index layer.

        If the requested or generated base key is already used by an Episodic episode, GHOST shall deterministically allocate the next available numeric suffix using the form:

        base_key_1
        base_key_2
        base_key_3

        and so on.

        The originally supplied key shall remain the base key; GHOST shall not overwrite the existing episode.

        The successful save result shall return the actual effective Recall Key that was stored.

        GHOST-MCP-MEMORY-RECALL
        Shared Recall Concept
        GHOST shall expose one Recall concept capable of selecting the appropriate retrieval path from the user's request.

        For Episodic Memory, Recall shall support:

        - deterministic exact retrieval when an exact Recall Key or exact Record ID is known; and
        - intelligent semantic retrieval when the user describes a memory without knowing its exact identifier.

        The two paths access the same Episodic Memory domain.
        REQUIREMENT
        		4.2.2
        GHOST-MCP-MEMORY-EXACT-RECALL
        Draft
        Parents:
        • GHOST-MCP-MEMORY-RECALL Shared Recall Concept
        GHOST-MCP-MEMORY-EXACT-RECALL
        Exact Recall
        An exact Recall Key or exact Record ID shall be handled deterministically.

        Exact identifiers shall directly select stored records within the authenticated owner's scope.

        Exact Recall shall not require semantic vector ranking.
        REQUIREMENT
        		4.2.3
        GHOST-MCP-MEMORY-NO-FAKE-EXACT-FILTER
        Draft
        Parents:
        • GHOST-MCP-MEMORY-RECALL Shared Recall Concept
        GHOST-MCP-MEMORY-NO-FAKE-EXACT-FILTER
        Exact Identifiers Are Not Intelligent-Retrieval Filters
        Recall Key and Record ID shall not be treated as approximate SQL narrowing filters for intelligent semantic retrieval.

        When an exact identifier is supplied, GHOST shall use the deterministic exact path.

        When the identifier is unknown, GHOST shall use the intelligent Episodic retrieval path defined in this document.

        GHOST-MCP-MEMORY-LIST
        Shared Memory List
        ghost_memory_list shall provide metadata discovery and navigation rather than full episode retrieval.

        The shared list capability shall be available for memory modes where listing is meaningful, except Clipboard Memory.

        The list capability may return identifying and descriptive metadata such as:

        - memory or conversation name;
        - memory type;
        - Recall Key;
        - Record ID;
        - Episode Title;
        - Episode Description; and
        - creation time.

        Stored full input/output bodies shall remain Recall content rather than List content.
        REQUIREMENT
        		4.3.2

        GHOST-MCP-MEMORY-LIST-FILTERS
        Deterministic List Filters
        The shared memory list operation shall support deterministic metadata filtering sufficient for practical discovery.

        Approved filter dimensions include:

        - memory or conversation name;
        - memory type;
        - date range; and
        - deterministic description matching.

        List shall not silently become semantic full-memory retrieval.

        GHOST-MCP-MEMORY-DELETE
        Deterministic Memory Delete
        ghost_memory_delete shall delete individual memory episodes only through an exact selector:

        - exact Recall Key; or
        - exact Record ID.

        Delete shall never use semantic similarity, a natural-language description, Episode Description similarity, vector retrieval, fuzzy matching, or an LLM decision to choose what data to destroy.

        GHOST-MCP-MEMORY-DELETE-DUPLICATE-SAFETY
        Duplicate Recall-Key Safety
        If an exact Recall Key resolves to multiple owner-scoped records, GHOST shall not silently choose an arbitrary record for deletion.

        The user shall be given deterministic identifiers sufficient to select the intended episode, or shall explicitly request deletion of all exact matches where that behavior is supported.
        REQUIREMENT

        Clipboard Excluded from Generic Delete
        Clipboard Memory shall not participate in the generic ghost_memory_delete operation.

        Clipboard lifecycle shall be controlled by its dedicated short-retention policy.

        GHOST-MCP-EPISODIC-ROOT
        Episodic Memory Scope
        Episodic Memory shall store ordinary persistent memory episodes that can later be recovered either:

        - directly through an exact Recall Key or Record ID; or
        - intelligently from a natural-language description.

        Direct Recall and intelligent retrieval shall be two access paths to the same Episodic Memory rather than separate memory types.
        REQUIREMENT

        GHOST-MCP-EPISODIC-DESCRIPTION-REQUIRED
        Episode Description Required for Episodic Save
        Each newly saved Episodic Memory episode shall contain a non-empty Episode Description.

        The description shall summarize the semantic content or useful meaning of that individual episode sufficiently to support later intelligent retrieval.

        The Episode Description shall not be replaced by the Episode Title.
        REQUIREMENT

        Episode Description Embedding
        The Episode Description shall have a precomputed vector representation available for intelligent Episodic retrieval.

        The description embedding shall be created from the stored Episode Description rather than generated dynamically from the complete episode during every recall.

        Intelligent Recall Query Description
        When the user requests a memory without knowing an exact identifier, ChatGPT shall formulate the semantic description of the memory being sought.

        That query description shall be embedded at recall time and compared against stored Episode Description embeddings.
        REQUIREMENT
        		5.5

        GHOST-MCP-EPISODIC-DATE-NARROWING
        Optional Date Narrowing
        Intelligent Episodic retrieval may first apply a deterministic SQL date-range filter when the user's request provides a relevant date or date interval.

        Date range is the approved deterministic narrowing dimension for the intelligent Episodic retrieval path.

        The intelligent path shall not invent key-prefix, title-prefix, or approximate Recall Key filtering as additional narrowing mechanisms.

        GHOST-MCP-EPISODIC-COSINE-RANKING
        Episode Description Similarity Ranking
        After any optional date narrowing, intelligent Episodic retrieval shall compare the query-description vector with stored Episode Description vectors using cosine similarity or the equivalent cosine-ranking behavior of the selected vector implementation.

        Ranking shall be based primarily on Episode Description semantics.

        GHOST-MCP-COLLECTION-DELETE-CONFIRMATION
        Two-Step Whole Collection Delete Safety
        Whole-Collection deletion shall use a temporary server-side confirmation state.

        For an authenticated owner and exact Collection ID, the first exact whole-Collection delete request shall not execute the deletion.

        The first request shall set the corresponding server-side delete-pending state to true and shall return a warning or refusal asking the client/user to repeat the same exact Collection deletion request.

        If the same owner repeats the exact whole-Collection delete request for the same Collection ID while that delete-pending state is true, GHOST shall execute the deletion and confirm the result.

        The delete-pending state shall be volatile server state and shall reset to false when the MCP server restarts.

        A future timeout or asynchronous reset policy may be added later, but no timeout duration or additional reset mechanism is fixed by this requirement.

        8. Current Implementation and Target Boundary
        TEXT
        The current MCP implementation already provides:

        - ghost_engineer_prompt;
        - ghost_memory_tag;
        - ghost_memory_recall;
        - ghost_memory_list; and
        - ghost_memory_delete.

        The current memory implementation already uses authenticated owner scoping and shared GHOST MemoryRecord/.ragmem/.ragmeta.json/SQLite infrastructure.

        The current implementation does not yet constitute the complete approved Episodic intelligent-retrieval, Clipboard, or Collection behavior defined above.

        Those requirements describe the approved target behavior and shall not be falsely reported as already complete.

        Exact future public tool identifiers for newly implemented Clipboard- and Collection-specific operations are intentionally not invented in this requirement document.
